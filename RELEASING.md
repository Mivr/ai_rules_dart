# Releasing

How a release of `rules_dart` and `rules_flutter` is cut from this repository. Each module has its own tag line,
its own release and its own registry entry. `rules_dart` goes first; then the floor of `rules_flutter` on it is set
by a commit; then `rules_flutter` goes.

| | `rules_dart` | `rules_flutter` |
|---|---|---|
| Tag | `rules_dart-v0.29.0` | `rules_flutter-v0.30.3` |
| Continues | `v0.28.3` | `v0.30.2` (a release of the old `Mivr/ai_rules_flutter`) |
| Release files | `rules_dart-v0.29.0.tar.gz`, `.docs.tar.gz`, one `.intoto.jsonl` attestation each | the same, `rules_flutter-v…` |
| Archive holds | `rules_dart/` only, under `rules_dart-0.29.0/`, `MODULE.bazel` at its top | `rules_flutter/` only |
| Workflows | `dart-tag.yaml` → `dart-release.yaml`; `dart-publish.yaml` by hand | `flutter-…` the same four |
| Registry templates | `.bcr/rules_dart/` | `.bcr/rules_flutter/` |

The version numbers are not in this file: the owner chooses them for each release. The first tag of a module must
be newer than its baseline in `.github/release.json` (`v0.28.3`, `v0.30.2`), which stands for the releases made
before the modules moved here; after that the module's own tags count. A tag whose release the gate refused stays
used: `rules_dart-v0.29.1` is the next number, never `v0.29.0` again.

## Off until the owner turns it on

Every job that tags, releases or publishes runs only when the repository variable `RELEASES_ENABLED` is `true`
(Settings > Secrets and variables > Actions > Variables; `gh variable set RELEASES_ENABLED --body true`). Unset,
every run of these workflows shows its jobs skipped. Two more switches stay separate:

- `AUTO_RELEASE_ENABLED` (with `RELEASES_ENABLED`) lets `dart-auto-release.yaml` and `flutter-auto-release.yaml` tag
  a commit by themselves after CI and Full pass. Leave it off for the first releases: `rules_flutter` must not be
  released before its floor commit.
- Publishing to the Bazel Central Registry is never called by a release. It is dispatched by hand (below), and needs
  the secret `BCR_PUBLISH_TOKEN` (a classic personal access token, name only here). Publishing `dart/runfiles` to
  pub.dev was removed from the release workflow on 2026-10-15 and is not part of this.

## Before the first tag

The owner decides: the merge of the pull request to `main`; the version of each release; whether the registry pull
requests are opened; whether `dart/runfiles` goes to pub.dev. A tag is made on `main`, on a commit that is
already on it.

Check, for the commit `S` to tag (`gh run list --workflow dart-ci.yaml --commit S --json event,conclusion,url`):

- `Dart CI` and `Dart Full matrix` each have a run on `S` that is a push to `main`, a nightly, or a dispatch, with
  conclusion `success`. The gate (`rules_dart/.github/workflows/release_gate.sh`) takes exactly that; when one is
  missing it dispatches it on the tag and waits (up to 350 minutes), so a missing run costs time, not a mistake.
- On a push to `main` the macOS legs are in `Dart Full` (`test-macos`); `mac-smoke` of `Dart CI` runs only on the
  nightly and on a dispatch. For `rules_flutter`, the macOS proof is `e2e-macos` of `Flutter Full`; `macOS Apple
  bundles` and `macOS toolchain resolution` of `Flutter CI` run only on a dispatch
  (`gh workflow run flutter-ci.yaml --ref main -f full=macos`). Read each run's `conclusion` job: it lists what must
  be green.
- The tag job and the gate do not look at macOS or Windows: reading those jobs is a person's step.

## Rehearse (no tag is created anywhere that matters)

A release can be rehearsed end to end in a scratch clone with no remote: clone, tag, and run the script the release
workflow runs.

```sh
git clone --no-hardlinks <this checkout> /tmp/rehearsal && cd /tmp/rehearsal
git remote remove origin && git remote add origin . && git config remote.origin.pushurl DISABLED
git tag -a rules_dart-v0.29.0 -m scratch
mkdir -p /tmp/out
RELEASE_OUT=/tmp/out .github/workflows/release_prep.sh rules_dart-v0.29.0 > /tmp/out/notes.txt
```

The script reads the public GitHub releases of the repository and, for `rules_flutter`, downloads the `rules_dart`
release its floor names: for a `rules_flutter` rehearsal before that release exists, put a `curl` on `PATH` that
serves a fixture. What to look at: `tar tzf` of the archive (`MODULE.bazel` under the prefix, no `e2e/` but
`e2e/smoke`, no `dev/`, no test-only directories; about 1.5 MB for `rules_dart`, 1.8 MB for `rules_flutter`); the
same bytes on a second run; `bazel build --nobuild //...` and the presubmit's `bazel test //...` in `e2e/smoke` of
the unpacked archive; a consumer workspace on `archive_override` blocks pasted from the notes; its
`MODULE.bazel.lock` regenerated byte for byte. The first rehearsal is recorded in the T23c report.

## Release `rules_dart`

1. **Choose the version.** `cd rules_dart/tools && bazel run //release:release -- latest --module=rules_dart` prints
   the latest (`v0.28.3` until the first tag). With the list of published tags
   (`gh api --paginate repos/Mivr/ai_rules_dart/releases --jq '.[] | select(.draft|not) | .tag_name' > published`),
   `bazel run //release:release -- next --module=rules_dart --to=S --published=$PWD/published` prints the version the
   commits suggest (`feat` or `!` bumps the minor). Preview the notes:
   `bazel run //changelog:changelog -- --tag rules_dart-v0.29.0`. A commit that touches both modules is in both notes.
2. **Turn the switch on:** `gh variable set RELEASES_ENABLED --body true`.
3. **Tag:** `gh workflow run dart-tag.yaml --ref main -f version=v0.29.0`. Do not push a tag by hand: that skips the
   checks of the tag job (on `main`, newer than the latest, not existing).
4. **Automatic after the dispatch:** the tag job creates the annotated tag `rules_dart-v0.29.0` on the commit it
   ran on and calls `dart-release.yaml`; its `gate` job waits for the proofs above; its `release` job (bazel-contrib's
   reusable workflow) loads `rules_dart/` (`bazel build --nobuild //...`), runs `release_prep.sh`, uploads the
   files, attests them and creates the GitHub release with the notes.
5. **A person checks the release:** it lists both archives and their attestations, and the notes start with an
   `archive_override` block. Paste that block into a fresh consumer (the README says how) and build.
6. **Registry (the owner's decision).** `gh workflow run dart-publish.yaml -f tag_name=rules_dart-v0.29.0` opens a
   draft pull request against `bazelbuild/bazel-central-registry` from the fork `Mivr/bazel-central-registry`, with
   the entry for `rules_dart/` only (`module_roots: rules_dart`, `tag_prefix: rules_dart-v`, templates in
   `.bcr/rules_dart/`). Mark it ready for review, wait for the registry's presubmit, and for the registry to serve
   the version (a merged pull request is not a served module: resolve it from a clean consumer).

## Prebuilt tools

A release ships each module's own tools prebuilt, so a consumer's first build compiles none of them
(`rules_dart/dart/private/prebuilt_tools.bzl` says how the rules use them; `rules_flutter/flutter/private/prebuilt_tools.bzl`
for Flutter's):

| Module | Set (`prebuilt_set`) | Keyed by |
|---|---|---|
| `rules_dart` | the module compiler of the default Dart SDK, `compile_wrapper`, `import_check`, `kernel_link` (AOT snapshots), `test_runner`, `kernel_launcher` (`exe`) | Dart version |
| `rules_flutter` | the module compiler of the bundled Dart SDK and the asset tool (AOT snapshots), `android_bundle` (`exe`) | Flutter version |

- The `tools` job of `dart-release.yaml` (and `flutter-release.yaml`) runs on each host platform the SDK tables list
  (`linux-x64`, `linux-arm64`, `macos-arm64`, `macos-x64`, `windows-x64`), on that platform's runner:
  `bazel run //release:release -- tools build --module=<module> --platform=<p> --out=<dir>` builds the set twice
  from the tag, in two consumer workspaces of the checkout with separate output bases and no cache, and writes
  `tools-<p>.tar.gz` only when the two builds agree byte for byte, with a sidecar `tools-<p>.json`. When they
  differ it writes only the sidecar, listing the files that differed, and that platform ships nothing: it builds
  its tools from source. A build that fails fails the job, and `release` needs every `tools` job.
- `release_prep.sh` runs `release tools table`: it checks each archive against its sidecar, copies it to the release
  files as `<tag>-tools-<version>-<p>.tar.gz` (attested like the archive), writes the table
  (`dart/private/prebuilt_tools.json`, `flutter/private/prebuilt_tools.json`: version → platform → url, sha256) into
  the module's archive in place of the checkout's empty one, and adds a line to the notes saying which platforms
  ship tools and which build from source.
- The table in the repository is empty: the repository, and a consumer on a path override, builds every tool from
  source. `--repo_env=RULES_DART_TOOLS=source` does the same for a consumer of a release, in both modules.
- An SDK bump needs nothing here: the release builds the tools of whatever SDK the tag pins.

To rehearse it, run `tools build` in the scratch clone before `release_prep.sh`, with `--out` naming
`<dir>/prebuilt-tools-<module>-<p>/`, and pass `RELEASE_TOOLS=<dir>`; a consumer then fetches the archive from the
URL in the table: `RELEASE_DOWNLOAD=file://<out>` makes the table and the notes name the files in `<out>`, which
must then hold `<tag>/<file>`.

## The floor of `rules_flutter`

7. On `main`, in `rules_dart/tools`: `bazel run //release:release -- floor set 0.29.0`. It writes the version in
   `rules_flutter/MODULE.bazel` (`bazel_dep` on `ai_rules_dart`), the floor table
   (`flutter/tests/dependency_floors.json`), `docs/dependencies.md`, `docs/ARCHITECTURE.md`, the README and every
   e2e workspace that names a floor; `bazel run //release:release -- floor check` fails, listing the places, when they
   differ. Inside the repository the number is inert (`local_path_override`), and a rehearsal showed the lockfiles
   identical before and after (`bazel run //refresh_locks -- --check rules_flutter` confirms). Commit it with a trailer
   such as `Changelog: Requires `ai_rules_dart` 0.29.0 or newer`, and get `Flutter CI` and `Flutter Full` green on
   that commit: it is the commit `S` of the next tag.

## Release `rules_flutter`

8. As steps 1 to 6 with the `flutter-` workflows, `--module=rules_flutter` and `rules_flutter-v…`. `flutter-tag.yaml`
   refuses the tag while the floor names a `rules_dart` that has no published (non-draft) release
   `rules_dart-v<floor>`, and `release_prep.sh` downloads that archive, checks its sha256 against the digest GitHub
   recorded for the release asset, and puts both `archive_override` blocks in the notes. The registry entry of
   `rules_flutter` needs `ai_rules_dart` at the floor on the registry first.

## Stop or undo

| Where it is | How to stop | How to undo |
|---|---|---|
| Before the tag | leave `RELEASES_ENABLED` unset, or `gh variable delete RELEASES_ENABLED` | nothing was done |
| Tag job ran, gate waiting | `gh run cancel <run>`; set the variable to `false` | `git push origin :refs/tags/<tag>`. The tag has no release; its number stays used |
| Gate refused (a CI or Full run failed) | nothing runs after it | the tag stays without a release: fix on `main` and release the next number |
| GitHub release created | — | `gh release delete <tag> --cleanup-tag --yes` (the attestation entries stay in the public log). A consumer that already pinned the archive keeps working; release the next number |
| Registry pull request open | close it | a merged one is undone by yanking the version in the registry's `metadata.json`, not by deleting it |
| Floor commit | `git revert` it before the `rules_flutter` tag | after the tag, release the next `rules_flutter` number |

## What a rehearsal cannot show

Nothing here has run in GitHub Actions: the tag job, the gate with the new names, the reusable workflow at this
layout, the attestations, the upload, the `publish-to-bcr` action with `module_roots`, the registry's presubmit on
Windows and macOS and with Bazel 9.0.0 and `rolling`, and whether the actions' token may create a tag of this
shape under the repository's rules. The first real tag is the first proof of those; watch it. For the prebuilt
tools, only a real release shows: the `tools` job on the macOS, Windows and Linux arm64 runners (and whether each
platform's builds are reproducible there), the upload of the job artifacts into the reusable workflow's build job,
and a consumer on each of those platforms that builds no tool.
